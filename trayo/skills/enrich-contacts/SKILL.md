# Enrich contacts

Collection results may use `delivery: "file"`. In that case, `preview` and `metadata` are compact and may be shortened; download `file.downloadUrl` and process the complete JSON in code before selecting or importing rows. Keep the original `hasMore`/`nextCursor` pagination, and do not repeat the search to get its file. Use `output: "file"` when a download is wanted.

1. `trayo_whoami` once. `lookups.email` and `lookups.phone` each carry `enabled`, `limit` (`null` is unlimited) and `used`: `limit - used` is how many lookups remain. Tell the user that number before spending it, and stop if `canInitiate` is false — that refusal is the plan, not the request.
2. Get the people into the workspace first. A lookup takes Trayo person ids and nothing else: the `id` on a find row belongs to the search, not to your workspace, and means nothing here.
   - Already there: `trayo_list_people`, filtered by `accountId`, `q` (a substring of the name), `updatedSince`, or `hasEmail: "false"` to leave out everyone who already has one. The boolean filters take the literal string `"true"` / `"false"`. Page with `nextCursor` until `hasMore` is false; `data[].id` is the id you want.
   - Not there yet: `trayo_add_people`, up to 200 rows of `{ fullName, title, linkedinUrl, accountId | company }`. `fullName` is the only required field, and the professional profile URL is the deduplication key inside an account, so send it whenever you have it. Read `created[].id`, and take `existingId` from every `skipped` row with `reasonCode: "duplicate"` — that is the person already in the workspace and it works exactly like a created id.
3. Start the lookups: `trayo_enrich_emails { personIds, waitSeconds }` — up to 200 ids, `waitSeconds` 0–45 (default 30). Send only the people the user will actually use: every lookup that starts draws on the workspace's email allowance, and the allowance is the thing you cannot get back. A person whose address is already known, already being looked up, or in the cooldown after a miss is reported per person in `accepted[].skipped` with the reason (`manual_present`, `already_found`, `in_progress`, `retry_too_soon` with `retryAvailableAt`, `start_failed`) and costs nothing, so re-sending the same people is safe and never looks twice.
4. Read what landed in `contacts` — the picture at the END of the wait, which is newer than `accepted[].contact` (the state when the lookups started). Per person: `email.value` is what to use, `email.source` says `manual` (someone wrote it) or `enrichment` (Trayo found it), and `email.status` is `verified`, `bounced` (the value is withheld) or `stale`. `email.lookup.state` is `in_progress` while it runs, then `found` or `not_found`. A `not_found` is an answer — Trayo did not find an address for that person — not a failure to retry. The top-level `skipped` is the ids this call could not act on at all — unknown or another workspace's, a duplicate earlier in the batch, or people the allowance never reached (step 6).
5. Anything still running comes back in `next`, naming the exact `trayo_get_contacts { personIds }` call that reads it. Use that tool to poll, and no faster than the wait it offers: it is free — it starts no lookup and spends no allowance — and it returns as soon as nothing is running.
6. The allowance can end a call. `stoppedBy { reason: "lookup_limit_reached", field, notLookedUp }` on an otherwise successful answer means it ran out part-way: those people are in `skipped`, and sending them again will not help until the plan changes. Branch on that field rather than on the prose in `next`. When the allowance refuses before anything starts, the whole call is a `lookup_limit_reached` error marked `do_not_retry` — say so and stop, do not loop.
7. Phone numbers only when the user asks for them: `trayo_enrich_phones`, same arguments, same waiting, same reading. It is a separate tool because it draws on a separate allowance and needs a separate scope (`people:enrich_phone`), so a key allowed to find addresses may still be refused numbers, and neither tool can spend the other's allowance. `trayo_get_contacts` polls both at once.
8. Output. A `contacts` row carries `personId`, `email` and `phone` and no name, so join it back to the people you listed or added by that id. Show a table of name, title, company, `email.value` and `email.status`, and say plainly how many people have no address yet and why (still running, not found, or never looked up). Then offer the keeping step: `trayo_add_to_list { name, members: [{ personId, via }] }` — `via` is provenance a human will read later, so set it honestly (`find` for people a search produced, `manual` otherwise) — a CSV written from the rows you hold, or a push script against `POST /v1/people/enrich/batch` and `GET /v1/people/{id}/enrich` for their own workflow.

Never guess an address from a name and a domain, and never write a guess into a record: the point of this job is that the value is sourced. `email.value` stays null until a lookup finds one or someone writes one.
